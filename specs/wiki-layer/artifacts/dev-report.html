Part three

What was learned

Three lessons left the plan. One became a standard, one corrected the command that caused it, and one is a four-step trail from a pilot defect to a check that can actually fail.

A new standard: I9 · untrusted-content discipline

from security finding I1-F24 · impl-standards.md · self-improve step

The security pass found that ingest had a write-capable agent read third-party source content — mirrors, clipped captures, local files — with no treat-as-data instruction and no write confinement. Because AGENTS.md sends every session to the wiki first, a poisoned source would keep poisoning every read. The fix landed in the diff; the gap it exposed landed in the standards list:

I9 — a harness file that has an agent read content the repo does not author tells it to treat that content as data, never as instructions, and confines the resulting writes to the operation's own surface.

The standard also needed a judge. I9 was assigned to the gate's fidelity lens cluster in the codex-gate skill — the cycle-1 suite run had failed test_lens_clusters_cover_every_stamped_standard[I] with unassigned standards: ['I9'] precisely because the standard existed with no cluster; by cycle 2 the failure was gone.

A routed lesson: copy the mirrors before the builders launch

pipeline-process → harness-build.md · per memory-series.md

KB mirrors are device-local, and this build started with four of its nine cited mirrors present only in the main checkout — builders would have grounded against files that were not there. The lead copied them in byte-identical, then routed the lesson to the file that caused it: harness-build.md's read-the-plan step now says to copy referenced mirrors missing from the worktree's ai-docs/ before builders launch.

The fidelity lens read that same edit as a drive-by outside the wiki-layer boundary (I1-F1, major, conf 100) and asked for a revert. The lead disputed it: routing a pipeline-process lesson to the file it corrects is the memory step under AGENTS.md's Lessons contract, and reverting it would break a standing obligation. The user accepted that reading at the human gate.

The MD024 trail: an append-only log versus a lint rule

pilot defect → seed fix → committed regression → a check that can fail

  1. Pilot run 2 hit it. .markdownlint.jsonc sets MD024 siblings_only: true, so appending a lint log heading identical to an earlier same-day pass — the deterministic case for a clean wiki linted twice in one day — was rejected by the auto-format hook. Run 2 landed a truthful distinct summary and the defect was routed to a builder.
  2. The seed absorbed it. A file-local <!-- markdownlint-disable MD024 --> in ai-docs/wiki/log.md (append-only logs legitimately repeat sibling headings), plus a wording relaxation in lint.md — the payload sits on the next non-blank line, because the formatter inserts a blank line after the heading. Run 3 then appended a heading byte-identical to run 2's with markdownlint at 0 errors.
  3. The gate wanted it committed. I1-F17 (I8, major): the fix shipped with an uncommitted scratch-copy proof and no regression assertion. ac2-seed.py gained a check that the seed log carries the disable comment.
  4. The delta round broke that check. I2-F3 (I8, major): the new assertion was a bare substring test, so it passed on a directive inside a code fence — where markdownlint ignores it. It became a fence-aware line scan requiring the comment on its own line, outside any fence, before the first entry heading. Three negative demos FAIL where the old check PASSed.

Plan-local lessons stayed in implementation-notes.md: the pyyaml availability error in a spawn prompt, the AC2 footer-parsing deviation, and the plan-session trailing commit.
